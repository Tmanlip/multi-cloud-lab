# MultiCloud Forge Observability

## 1. Overview

MultiCloud Forge implements observability independently for its AWS and
Azure serverless workloads.

The monitoring architecture is designed to detect application failures
while using the monitoring services native to each cloud platform.

The implementation consists of:

-   AWS CloudWatch monitoring for AWS Lambda
-   Azure Monitor scheduled query alerts
-   Application Insights telemetry
-   Log Analytics workspace queries
-   Controlled failure endpoints for observability testing
-   Health endpoints for availability validation

The monitoring resources are managed through Terraform.

## 3. AWS Monitoring

AWS monitoring is defined in: terraform/modules/aws-lambda/monitoring.tf

The Lambda function is monitored using the native AWS Lambda Errors
metric. Terraform creates the following resource:
aws_cloudwatch_metric_alarm.lambda_errors

The alarm name follows the Lambda function name: mcf-dev-health-errors

## 4. AWS CloudWatch Error Alarm

The alarm monitors: Namespace: AWS/Lambda Metric: Errors Statistic: Sum
Period: 300 seconds Evaluation periods: 1 Threshold: 1 Comparison:
GreaterThanOrEqualToThreshold

The alarm is scoped specifically to the deployed Lambda function
through: FunctionName = aws_lambda_function.health.function_name

Therefore, errors generated by unrelated Lambda functions do not affect
this alarm. The alarm triggers when: Lambda Errors \>= 1 within a
5-minute evaluation period

## 5. AWS Missing Data Behaviour

The alarm uses: treat_missing_data = "notBreaching"

This prevents periods with no Lambda invocations from being interpreted
as failures. For example: No requests \| v No Lambda error datapoints \|
v Missing data treated as non-breaching \| v Alarm remains OK

This behaviour is suitable for a low-traffic lab environment where the
Lambda function may not receive requests continuously. \## 6. AWS Logs
Lambda execution logs are written to CloudWatch Logs. The log group
follows: /aws/lambda/mcf-dev-health

Logs can be inspected using: aws logs tail "/aws/lambda/mcf-dev-health"
`--region ap-southeast-1` --since 10m

A normal invocation produces Lambda lifecycle entries such as: START END
REPORT

Runtime information includes execution duration, billed duration, memory
allocation, and memory consumption. \## 7. AWS Failure Testing The
Lambda application includes an intentional failure route for controlled
observability testing. The failure endpoint causes the Lambda invocation
to fail intentionally. A failure generates an exception similar to:
RuntimeError: Intentional MultiCloud Forge observability test failure

CloudWatch records the invocation as an error, contributing to the
Lambda Errors metric monitored by Terraform. This provides an end-to-end
test path: Failure request \| v AWS Lambda \| v Runtime exception \|
+------\> CloudWatch Logs \| v AWS/Lambda Errors metric \| v CloudWatch
Alarm

The failure endpoint is intended only for controlled testing. \## 8.
Checking the AWS Alarm The current alarm can be inspected with: aws
cloudwatch describe-alarms `--alarm-names "mcf-dev-health-errors"`
--region ap-southeast-1
`--query "MetricAlarms[0].{State:StateValue,Reason:StateReason}"`
--output json

Possible CloudWatch alarm states include: OK ALARM INSUFFICIENT_DATA

Because the alarm evaluates a five-minute period, a newly generated
failure may not immediately change the alarm state. \## 9. Azure
Monitoring Architecture Azure monitoring uses a different telemetry
path. The Function App is integrated with Application Insights.
Application Insights is workspace-based and sends telemetry into a
managed Log Analytics workspace. The resulting architecture is: Azure
Function \| v Application Insights \| v Log Analytics Workspace \| v
AppRequests \| v Scheduled Query Rule \| v Azure Monitor Alert

The Terraform implementation is located in:
terraform/modules/azure-function/monitoring.tf

## 10. Application Insights Integration

The Azure Function Terraform module creates:
azurerm_application_insights.function

The Function App receives the Application Insights connection string
through its configuration. The resulting application setting is:
APPLICATIONINSIGHTS_CONNECTION_STRING

The Function App is therefore connected to the Application Insights
resource created by Terraform. \## 11. Workspace-Based Application
Insights The Application Insights resource operates using:
IngestionMode: LogAnalytics

Telemetry is stored in the associated Log Analytics workspace. For this
environment, Application Insights telemetry includes tables such as:
AppRequests AppTraces AppExceptions AppDependencies

During validation, telemetry was successfully observed in: AppRequests
AppTraces

## 12. Azure HTTP Request Telemetry

HTTP requests to the Azure Function are recorded in: AppRequests

Relevant request telemetry includes: TimeGenerated Name ResultCode
Success Url

For example, the health endpoint generated: Name: health ResultCode: 200

while the controlled failure endpoint generated: Name: fail ResultCode:
500

This telemetry provides the data source for the Azure error alert. \##
13. Azure Scheduled Query Alert Terraform creates:
azurerm_monitor_scheduled_query_rules_alert_v2.function_errors

The alert name follows: `<function-app-name>`{=html}-errors

For the development environment: func-mcf-dev-77675-errors

The alert is enabled with: Severity: 2 Evaluation frequency: 5 minutes
Window duration: 5 minutes Threshold: 1

## 14. Azure Alert Query

The scheduled query evaluates the AppRequests table: AppRequests \|
where ResultCode startswith "5" \| summarize ErrorCount = count()

The query identifies HTTP server errors by filtering requests whose
result codes begin with: 5

Examples include: 500 502 503

The query then counts the number of matching requests. \## 15. Azure
Alert Condition Terraform evaluates the query result using: Metric
measure column: ErrorCount Aggregation: Total Operator:
GreaterThanOrEqual Threshold: 1

The alert therefore triggers when: ErrorCount \>= 1

within the configured five-minute monitoring window. Only one failing
evaluation period is required. \## 16. Azure Alert Scope The scheduled
query is scoped to: azurerm_application_insights.function.workspace_id

This is important because the AppRequests table exists in the Log
Analytics workspace associated with the workspace-based Application
Insights deployment. The monitoring query therefore executes against the
workspace containing the actual Function App request telemetry. \## 17.
Azure Failure Endpoint The Azure Function contains a controlled failure
route: /api/fail

The endpoint intentionally returns: HTTP 500 Internal Server Error

with a response identifying it as an observability test failure. It can
be triggered with: curl.exe -i \`
"https://`<function-app>`{=html}.azurewebsites.net/api/fail"

The expected result is: HTTP/1.1 500 Internal Server Error

This request is subsequently ingested into Application Insights and the
Log Analytics workspace. \## 18. Querying Azure Failure Telemetry The
workspace can be queried for HTTP 5xx requests using: AppRequests \|
where TimeGenerated \> ago(1h) \| where ResultCode startswith "5" \|
project TimeGenerated, Name, ResultCode, Url \| order by TimeGenerated
desc

The expected controlled failure appears as: Name: fail ResultCode: 500

This confirms the complete telemetry path: Azure Function \| v HTTP 500
\| v Application Insights \| v Log Analytics AppRequests

## 19. Azure Alert Validation

The scheduled query alert can be inspected using: az monitor
scheduled-query show `--name "func-mcf-dev-77675-errors"`
--resource-group "rg-mcf-dev-sea"
`--query "{Name:name,Enabled:enabled,Severity:severity,Scopes:scopes}"`
--output json

The deployed configuration should report: Enabled: true Severity: 2

## 20. Azure Fired Alert Validation

After generating a controlled HTTP 500 response and allowing the
scheduled query to evaluate, Azure Alerts Management can be used to
verify that the alert fired. The successful observability test produced:
Alert: func-mcf-dev-77675-errors Monitor condition: Fired Monitor
service: Log Alerts V2 Severity: Sev2 Signal type: Log

This demonstrates that the full monitoring path is operational:
/api/fail \| v HTTP 500 \| v Application Insights \| v Log Analytics \|
v Scheduled Query Rule \| v Azure Monitor \| v ALERT FIRED

## 21. Health Monitoring vs Error Monitoring

MultiCloud Forge separates availability testing from error monitoring.
Health validation The endpoints: AWS: /health

Azure: /api/health

are used by: tests/connectivity/test_health.py

to verify that both workloads are reachable and healthy. Error
monitoring The controlled failure endpoints generate telemetry used to
validate the monitoring systems. Therefore: Health Test \| +--\> Is the
application operational?

Error Monitoring \| +--\> Are application failures being detected?

These serve different operational purposes. \## 22. AWS and Azure
Monitoring Comparison Component AWS Azure Compute AWS Lambda Azure
Functions Telemetry source Lambda metrics Application Insights Log
platform CloudWatch Logs Log Analytics Error signal Lambda Errors HTTP
5xx requests Detection mechanism Metric alarm Scheduled log query
Evaluation window 5 minutes 5 minutes Threshold \>= 1 error \>= 1 HTTP

The difference is intentional: each platform uses its native

behaviour. \## 23. Observability Validation Strategy The monitoring
system was validated through controlled failures rather than waiting for
accidental production errors. The test process is: Deploy \| v Verify
health \| v Generate controlled failure \| v Inspect logs/telemetry \| v
Verify alert

This provides evidence that the observability configuration is
functional rather than merely provisioned. \## 24. Current Observability
Coverage The project currently provides: - AWS Lambda execution
logging - AWS Lambda error metrics - AWS CloudWatch error alarm - Azure
Function request telemetry - Azure Application Insights integration -
Azure Log Analytics telemetry - Azure HTTP 5xx detection - Azure
scheduled query alert - Controlled failure injection - Multi-cloud
health validation This establishes the monitoring foundation for
MultiCloud Forge. Future improvements could include centralized
dashboards, notification action groups, latency monitoring, availability
tests, distributed tracing, and cross-cloud incident correlation.
